# Техническое задание

## Задача

Сделать локального помощника для выбора фильмов MovieLens 100K. Он должен
использовать существующий рекомендательный модуль и новую LightGCN, а не
заменять ранжирование выдуманным списком LLM. Пользователь — один оператор
учебной программы на Mac, выбирающий ID пользователя из датасета.

## Вход и результат

На вход подаются user_id > 0 и русский текст длиной 1–1500 символов. Допустимы
рекомендации, история оценок, поиск названия и сравнение item-CF с LightGCN.
Число фильмов — от 1 до 5. Выход — JSON со статусом, планом, точными ID,
названиями, жанрами и объяснениями. Источником каталога является u.item,
источником известной истории — только train. Test не становится памятью агента.

Если данных нет, вернуть no_results с пояснением. Если независимая проверка
дважды отклонила черновик, вернуть rejected без списка. Недоступность движка
должна завершаться ошибкой, записанной в наблюдаемость, без фиктивного ответа.

## Состав системы

1. LangGraph управляет общим State и узлами planner → tools → writer → validator.
2. Planner выбирает инструмент и параметры по JSON-схеме, включая жанры и запреты.
3. MovieTools исполняет только recommend/history/search/compare/refuse.
4. Writer выбирает ID из evidence и объясняет их только доступными жанрами/методом.
5. Validator другого семейства LLM оценивает черновик. Код проверяет ID, число
   фильмов и повторы. При замечаниях разрешена одна доработка.
6. Как минимум три LLM испытываются на одинаковых задачах. Их версии,
   квантизация, параметры, исходные ответы и время сохраняются.

Запрос не может менять user_id, исполнять shell/SQL, открывать произвольные файлы
или выполнять сетевой поиск. Названия и жанры подставляются из каталога кодом.
При рекомендациях исключаются все train-seen фильмы, даже с низкой оценкой.
Запрет жанра имеет приоритет над предпочтением; полный конфликт даёт no_results.

## Память и запуск

Три слоя: State одного запуска, кеш инструментов с TTL 1 час, явный профиль
пользователя с TTL 30 дней. Изменение профиля увеличивает revision и очищает кеш.
Версия каталога и checkpoint входит в ключ. Изменение файлов требует перезапуска.
Истечение TTL проверяется при чтении. Нужны команды изменения и удаления профиля.

Основной запуск — macOS ARM64 + llama.cpp CPU в Seatbelt sandbox. Политика
разрешает чтение нужного кода/весов и loopback-порт LLM, запись только в runtime.
Изоляция проверяется настоящими probes, включая запреты файла/сети и остановку
своего дочернего процесса. Варианты VM, MicroVM, контейнера и runtime sandbox
сравниваются отдельно; ограничения выбранного варианта не скрываются.

## Оценка и критерии проверки

- Product: доля полностью выполненных задач в шести заданных E2E-сценариях;
  точность выбора tool, соблюдение количества и фильтров. CTR/retention только
  как план будущего A/B-теста, без чисел из искусственной симуляции.
- LLM: точность routing/выбора ID/вердикта, корректность схемы отдельно от смысла,
  число токенов и время. Judge проверяется также на заведомо неверных ответах.
- RecSys: одинаковый test для шести методов, NDCG/Recall/Precision/MAP/HitRate@10,
  покрытие, latency и парный bootstrap. Подбор GNN только по validation.
- Infrastructure: полное время p50/p95, ошибки, timeout, память процесса с явной
  областью измерения, работа экспортера и свежесть телеметрии.
- Observability: реальные OTel spans, логи, траектории, Prometheus endpoint,
  локальные алерты и непрерывный монитор. Отдельный контролируемый отказ движка
  должен создать error span, счётчик ошибки и алерт.

Проверка завершена, когда код запускается в указанном окружении, тесты проходят,
все испытания выполнены, результаты сохранены, а ограничения и неудачи отражены
в отчёте. Доля успехов маленьких LLM измеряется, а не подгоняется под обещание.
